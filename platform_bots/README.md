# Заготовка: мультиплатформенные боты

Из СВОДКА_ПРОЕКТА.md, раздел «Не начато / в планах»:
«Мультиплатформенные боты (Telegram и др.) — архитектура пока не заложена, только VK».

Этот пакет — черновая архитектура под несколько платформ (Telegram,
MAX, Одноклассники, и по тому же образцу можно добавить любую другую).
**Ничего здесь не подключено к живому боту** и не запускается ни одним
systemd-сервисом — это стартовая точка, а не готовая к продакшену
интеграция. Раскладка:

- `base_adapter.py` — интерфейс `MessagingAdapter` (send_message + run) и
  нейтральный формат клавиатуры (список рядов кнопок-строк).
- `telegram_adapter.py` — рабочий черновик поверх официального Telegram
  Bot API. Можно проверить прямо сейчас, если завести токен через
  @BotFather (см. блок `if __name__ == "__main__"` внизу файла).
- `max_adapter.py`, `ok_adapter.py` — 03.09.2026 сверены с реальной
  официальной документацией (dev.max.ru и apiok.ru соответственно, не
  просто "правдоподобная структура"): базовый URL, схема авторизации,
  точные методы отправки сообщения и приёма апдейтов (long polling) —
  подтверждены цитатами из доки (ссылки — в докстринге каждого файла и в
  СВОДКА_ПРОЕКТА.md, журнал изменений). Осталось НЕ подтверждено (везде
  явно помечено `TODO: сверить с докой`, по 2-3 пункта на файл) — в
  основном точные поля кнопок клавиатуры и пара пограничных URL-путей,
  которые доке не удалось найти текстом. Перед реальным использованием —
  завести токен и проверить `if __name__ == "__main__"` в каждом файле
  (по образцу `telegram_adapter.py`), особенно кнопки.

## Почему не переписано сразу в vk_bot/

`vk_bot/exercises/base.py::BaseExercise.send_message` сейчас напрямую
дёргает `self.vk.method('messages.send', ...)`, а `vk_bot/keyboards.py`
строит клавиатуры через `VkKeyboard`/`VkKeyboardColor` из `vk_api` — то
есть вся логика упражнений (`vk_bot/exercises/*.py`, 6 упражнений, 253
теста) завязана на VK-специфичный формат прямо в теле каждого экрана.
Переписать это одним махом — рискованная, трудноотменяемая правка
прямо в работающем проде с живыми пользователями, без возможности
проверить на реальном Telegram/MAX/OK-аккаунте прямо сейчас. Поэтому
здесь только сама архитектура на будущее, не тронувшая ни строчки в
`vk_bot/`.

## План миграции, когда решите подключать по-настоящему

Шаги ниже — в порядке от самого безопасного к тому, что реально меняет
поведение. Каждый шаг можно откатить, не трогая следующий.

1. **Завести токен и проверить адаптер отдельно от бота.** Например для
   Telegram: `TELEGRAM_BOT_TOKEN=... python -m platform_bots.telegram_adapter`
   — эхо-бот, ничего общего с упражнениями, просто проверка, что
   адаптер реально шлёт и получает сообщения.

2. **Развести нейтральные клавиатуры.** Сейчас каждая функция в
   `vk_bot/keyboards.py` возвращает готовый VK JSON. Нужно, чтобы
   каждая функция возвращала нейтральные ряды (`[["➡️ Продолжить"],
   ["🔄 Начать заново и сохранить"], ["💾 Выйти и сохранить"]]`), а
   готовый VK-объект собирался ОТДЕЛЬНОЙ функцией-конвертером в самом
   конце, только там, где клавиатура реально уходит в `vk.method(...)`.
   Текстовые константы (`CONTINUE_TEXTS`, `ADVANCE_TEXTS` и т.д.) не
   меняются вообще — они и так платформонезависимы (просто множества
   строк для распознавания нажатий).

3. **Завести `self.platform` в `BaseExercise`.** `__init__` принимает не
   `vk_session`, а любой объект с интерфейсом `MessagingAdapter`;
   `send_message` внутри `BaseExercise` зовёт
   `self.platform.send_message(user_id, message, keyboard)` вместо
   прямого `self.vk.method(...)`. Для VK — просто оборачивает
   существующий `self.vk.method('messages.send', ...)` в класс
   `VkAdapter(MessagingAdapter)`, поведение не меняется ни на бит (это
   и есть первая проверка: старые 253 теста должны остаться зелёными
   без единой правки в них самих, раз внешнее поведение не изменилось).

4. **Только теперь — новый входной цикл под конкретную платформу**, по
   образцу `vk_bot/main.py`: свой `main_telegram.py`
   (`TelegramAdapter().run(on_message)`, где `on_message` — тот же
   диспетчер по `user_sessions`/exercises, что уже есть для VK, просто
   без vk-specific частей типа longpoll-событий). Отдельный процесс,
   отдельный systemd-сервис (`observer_bot_telegram` рядом с
   `observer_bot`) — VK-бот это не касается вообще.

## Модель пользователя — было ловушкой, теперь решено (03.09.2026)

ID пользователя РАЗНЫЙ на каждой платформе (VK user_id, Telegram
chat_id, OK user_id — разные числа/форматы, никак не связанные между
собой). `bot_api.User` уже хранит и `vk_id`, и `telegram_id` (оба
`null=True, blank=True` — миграция 0009), а `max_id`/`ok_id` заводятся
по тому же образцу, когда эти адаптеры реально подключат к боту.

Привязка ОДНОГО человека к нескольким платформам сразу — то есть
объединение прогресса, напоминаний и проверок между VK- и
Telegram-аккаунтом одного и того же человека — реализована: код
подтверждения (`bot_api.AccountLinkCode`, живёт 10 минут), который
генерируется в одном мессенджере и вводится в другом (пункт меню
«🔗 Привязать аккаунт» в `vk_bot/keyboards.py`/`handlers.py`,
эндпоинты `POST /link/generate/` и `POST /link/confirm/` в
`bot_api/views.py::AccountLinkViewSet`). Слияние аккаунтов —
`_merge_users()` в `bot_api/views.py`: переносит результаты/отзывы,
берёт максимум по streak, более свежий прогресс при конфликте по
упражнению, дедуплицирует одинаковые напоминания, старый аккаунт
удаляется. Аккаунты с уже занятыми ОБОИМИ id (конфликт) или уже
полностью привязанные — отдельные честные ошибки, а не молчаливый сбой.
Подробности и известные решения по merge-политике — см.
СВОДКА_ПРОЕКТА.md, запись от 03.09.2026 («Привязка аккаунтов»).
